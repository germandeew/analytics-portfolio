# Учёт денег с правилами внутри PostgreSQL

Маленькая, но честная модель денежного учёта: счета, проводки, сторно, остатки, роли и изоляция строк.
Главная идея — правила денег живут в базе, а не только в приложении. Тогда их нельзя обойти ни
скриптом, ни новой ручкой API, ни ошибкой в коде, и каждое правило стережёт тест.
Мутационное тестирование проверяет, что тесты действительно ловят поломку каждого правила.

Данные выдуманные. Код написан с нуля для портфолио.

## Правила и их охрана

| Правило | Как держится в базе | Тест |
|---|---|---|
| Проводка сбалансирована: сумма строк = 0 | отложенный constraint trigger, проверка при commit | 8, 9 |
| Строка проводки не нулевая | `check (amount <> 0)` | 10 |
| Проводки без строк не бывает | отложенный constraint trigger | 11 |
| История не переписывается | триггеры запрещают `update`, `delete`, `truncate`; ошибку исправляет сторно | 12–14 |
| Сторно — обратные знаки, одно на проводку | команда `reverse_entry` + `unique` на ссылке | 15, 16 |
| Перевод: сумма > 0, разные счета, одна валюта, хватает остатка | команда `post_transfer` | 1–7 |
| Системная касса может уходить в минус, клиентские счета — нет | флаг `overdraft_allowed` | 6, 7 |
| Клиент видит только свои счета и остатки | row level security + представление с `security_invoker` | 17, 18 |
| Клиент не пишет деньги, приложение пишет только через команды | права: `revoke ... from public`, `security definer` | 19, 20 |

## Решения, которые стоит обсудить

- **Остатки не хранятся, а считаются из строк.** Расхождению «остаток против истории» негде появиться.
  Для больших объёмов можно добавить материализованные остатки, но сверять их с историей тем же тестом.
- **Баланс проверяется в конце транзакции.** Проводка записывается несколькими строками, и
  промежуточное состояние законно несбалансировано. Поэтому триггер `deferrable initially deferred`.
- **Оба счёта блокируются в одном порядке** (`order by account_id for update`): параллельные переводы
  не проскочат проверку остатка и не устроят взаимную блокировку.
- **Сторно не проверяет остаток.** Это исправление ошибки, а не новый платёж: остаток может стать
  отрицательным, и это должно быть видно в отчёте, а не спрятано отказом.
- **Команды — `security definer` с фиксированным `search_path`.** Права на функции по умолчанию есть
  у PUBLIC, поэтому их нужно отзывать явно. Мутации 17 и 18 проверяют, что тесты это заметят.

## Запуск

Нужен PostgreSQL 15+ и `psql`. Самый простой путь — Docker:

```bash
docker compose up -d
export PGHOST=127.0.0.1 PGPORT=5433 PGUSER=postgres PGPASSWORD=demo
make test      # схема, данные и 20 тестов
make mutate    # мутационное тестирование
```

## Мутационное тестирование

`mutate.py` по очереди портит одно правило в `schema.sql` (19 мутаций), поднимает чистую базу и
гоняет тесты. Тесты упали — мутант «убит». Тесты прошли — правило можно сломать незаметно.
Если после правки схемы фрагмент мутации перестал находиться, скрипт падает: список не
устаревает молча.

Результат на PostgreSQL 18.6:

```text
 1. убит   баланс проводки: ловим только перекос в плюс
 2. убит   строка с нулевой суммой разрешена
 ...
18. убит   сторно доступно всем ролям
19. пропуск проверка баланса работает с правами того, кто делает commit (эквивалентна на PostgreSQL 18)

Убито 18 из 18, пропущено 1.
```

### Находка про версии PostgreSQL

Мутация 19 убирает `security definer` у проверки баланса. На PostgreSQL 18 она выжила, и
разбор показал причину: начиная с 18-й версии отложенный триггер выполняется с ролью, которая
поставила событие в очередь. Здесь это владелец команды `post_transfer`, у которого есть права на
чтение строк. На версиях 15–17 тот же триггер выполнялся бы с ролью на момент commit, то есть с
ролью приложения без прав на чтение, и commit упал бы. Поэтому `security definer` остаётся ради
совместимости, а мутация помечена как зависящая от версии. На 18 она пропускается, на 15–17 тест 20
должен её убивать (на 15–17 это не проверялось).

## Что бы добавил в боевой системе

- Ключ идемпотентности у команд, чтобы повтор запроса не провёл деньги дважды.
- Журнал аудита: кто и с какой ролью вызвал команду.
- Проверку баланса один раз на проводку, а не на каждую строку (transition tables).
- Ночной прогон мутаций в CI и запрет выкатки при выжившем мутанте.
